# Charter interfaces and reusable foundations

Charter owns the functional contracts used by downstream applications. It provides interfaces plus optional `Abstract*` extension points and complete `Base*` implementations where a neutral reusable default is possible. The specification, schemas, conformance corpus, and Go SDK require no platform; optional adapters may connect Charter to Keel, Scout, or another implementation.

## SDK contracts

- [x] Generate or maintain typed SDK models for every schema in `schema/catalog.json`, including document envelopes, references, versions, and namespaced extensions (`sdk/model`, hand-maintained per schema domain and round-trip tested against every Harbor document and its schema).
- [x] Define provider/resolver interfaces for organization, process, architecture, identity, authority, capability, binding, evidence, and information-governance documents. Organization interfaces are neutral and do not implement organization management.
- [x] Define authorization, approval, capability invocation, policy, evidence, and conformance request/decision interfaces with fail-closed results and stable requirement identifiers (`authority.Evaluator`/`ApprovalGate`, `capability.Invoker`, `information.Evaluator`, `evidence.Sink`, `validate.Runner.Claim`).
- [x] Keep SDK contracts platform-neutral and provide optional adapters for Keel's principal, evaluator, invocation, event, and validation ports. Keel never depends on Charter, and Charter never depends on Scout. (`sdk/adapter/keel` against keel v1.2.55: `Session`/`IdentityMap`/`Caller` for the principal, `PermissionGate` over `CheckActionPermission` as the evaluator, `GuardedInvoker` over trust guards for invocation, `TableLogStore`/`PublishingSink` over `port.TableLogger`/`port.MessagePublisher` for evidence events, `BigintIDs`, `MetricsInvoker`. Validation stays in `sdk/validate`; keel has no validator port, as `todo_keel.md` records.)

## Reusable foundations

- [x] Provide `Abstract*` extension points with compile-time interface assertions: `AbstractEvaluator` and `AbstractApprovalGate` (authority), `AbstractInvoker` (capability), `AbstractSink` (evidence), `AbstractDocumentProvider` (corpus), `AbstractBinding` (binding), `AbstractResolver` (identity), with `Base*` defaults where a complete neutral implementation exists.
- [x] Provide reusable reference resolution, effective-time evaluation, delegation-depth/limit evaluation, binding feature comparison, and append-only evidence helpers.
- [x] Keep persistence and external-system adapters pluggable: `corpus.Source`, `evidence.Store`, and `binding.VendorMapping`/`Executor` are the injection points; Charter, Keel, and Scout do not manage organizations.

## Conformance rules and fixtures

- [x] Publish schemas for the conformance manifest, rule definition, and fixture descriptor formats (`schema/conformance/manifest`, `rule_definition`, `fixture_descriptor`; `ManifestReader` validates every file against them).
- [x] Implement the validator interface for structural validation, semantic rule execution, fixture execution, and `ConformanceClaim` generation.
- [x] Require every active rule to parse, cite normative requirements, have deterministic pass/fail semantics, and include schema-valid positive and negative fixtures with declared additional failures (`Runner.RunManifest` rejects manifests that violate this).
- [x] Run every active fixture in CI and verify exact rule outcomes; a valid fixture must pass all selected rules and an invalid fixture must fail every declared rule (`.github/workflows/ci.yml` runs gofmt, vet, and `go test -count=1 ./...`, which executes every manifest fixture through `validate.Runner`).
- [x] Activate agent-runtime and system-adapter profiles only when their executable rules and fixtures are present (agent-runtime: eight runtime-behavioral rules against `validate.Subject`; system-adapter: four against `validate.AdapterSubject`; every rule has a must-carry-out and a must-refuse scenario).

## Remaining work

Reviewed on 2026-08-25 after the SDK, CLI, keel adapter, and all three conformance profiles landed. Every item above is done; these are the gaps the implementation itself exposed, in priority order.

- [x] Information-governance gate in the invocation pipeline (`Invocation.InformationUses`, evaluated after separation of duties, with decisions recorded in the action record's `informationEvaluations`; rule CHR-RULE-RT-007): let an invocation declare the information it uses and its purpose, evaluate `Use` per declaration before execution, record the decisions in the action evidence, and add runtime-behavioral carry-out and refuse scenarios (CHR-INFO-002, CHR-INFO-007, CHR-INFO-008).
- [x] Exception and escalation output (`capability.Escalator`, `BaseEscalator` over `BaseAccountableRecipient`, run by the invoker for unknown and failed outcomes; rule CHR-RULE-RT-008): an unknown outcome or a denial today ends in a `Result`; nothing produces the `ExceptionRecord` and `Escalation` the spec expects when an agent must stop or escalate. Add a neutral helper that turns such results into appended exception and escalation records, and a behavioral rule that an unknown outcome yields an escalation (CHR-AGENT-004, CHR-EVID-006, CHR-EVID-007).
- [x] Event delivery contract (`binding.AbstractEventConsumer` + atomic `DeliveryLedger`, `agent.Triggered`): at-most-once and at-least-once event ids are claimed before handling, failed at-least-once claims are released for retry, and exactly-once is rejected because it requires a shared transaction with the handler. Scout needs this for every event-driven path (CHR-SEC-008; see `todo_scout.md`).
- [x] Evidence redaction before append (`evidence.Redactor`, `BaseRedactor` default in `NewBaseMemorySink`, applied by `keel.PublishingSink` too): reasons and adapter errors are copied verbatim into `ActionRecord`s, so vendor error text can carry secrets into evidence. Add a redaction hook on `evidence.AbstractSink` with a neutral default and a test that a scripted vendor secret never reaches the store (CHR-SEC-005, CHR-SEC-010).
- [x] Evidence bundle assembly (`evidence.Queries.RecordsAbout`, `AbstractSink.Assemble`): provide `evidence.Queries.BundleFor(subject)` that collects every record about a process instance in order and hands it to `AbstractSink.Bundle` for a chained integrity value, so runtimes do not assemble bundles by hand (CHR-EVID-005).
- [x] Normative follow-ups recorded in the ADRs: CHR-EVID-010 with `ActionRecord.disposition` and `informationEvaluations` and rule CHR-RULE-CAP-001 (ADR 0003); `x-charter-ref-kinds` on every `idRef` property, making CHR-RULE-CONF-002 schema-driven (ADR 0004); CHR-CONF-013 and CHR-CONF-014 in `spec/12_conformance.md` (ADR 0005).
- [x] First release 1.0.0: `draft` replaced across `spec/`, `schema/`, `conformance/`, and the examples; `migration_guide.json` added; the reference SDK's `core-model`, `agent-runtime`, and `system-adapter` claims generated into `conformance/claims/` and kept current by a test. Remaining maintainer steps: review, commit, tag `v1.0.0`. From the next release on, the 1.0.0 fixtures stay runnable to honour CHR-CONF-010.
- [x] Keel round two (`keel.Gate` middleware, table-action handler, and worker `Check`/`JobContext`; `TableLogStore` preservation fixture; tenant scoping via keel v1.2.55). Nothing is requested from keel; a generic pre-action port and a queryable `port.TableLogger` destination stay noted in `todo_keel.md` as upstream candidates.
