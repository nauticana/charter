# Keel interfaces required by Charter

Keel remains a domain-independent backend framework. It supplies generic ports that an optional Charter adapter can use; it does not own Charter documents, organization management, actor lifecycle, or authority semantics.

Reviewed against keel v1.2.55 on 2026-08-25: none of the items below is keel work today. Round two is adapter work in `charter/sdk/adapter/keel`; the only candidate for keel is a generic pre-action port (principal, operation, resource, opaque context, action time → allowed / denied / missing / error) called from inside `RestHandler`, `TableService`, table actions, and `JobExecutor`, and it is taken only if the adapter's middleware and wrappers prove insufficient for generated CRUD endpoints. Keel already exposes the primitives an adapter needs (`port.Principal` + `common` context keys for identity and tenant, `CheckPermission` and `guard.GuardChain` for admission, `port.TableLogger` for row-change audit, `RequestID` for tracing); everything Charter-shaped on top of them — decision semantics, invocation envelopes, event and report schemas, validation rules, fixtures — belongs to the Charter SDK or the adapter. Keel takes a new generic port only when an implemented adapter demonstrates the shape.

## Principal and decisions

- [x] **addressed in the Charter adapter** — `port.Principal` plus the `PartnerID` / `ApiKeyID` / `AuthPrincipal` context keys feed `keel.Session`, `IdentityMap`, and `Caller`, preserving the opaque subject, tenant, credential, authentication claims, and transport scopes without treating scopes as domain authority.
- [x] **addressed in the Charter SDK and adapter** — `authority.Evaluator` carries the actor, capability, resource and organizational context, action time, and measures; its decision distinguishes `allowed`, `denied`, `missing`, and `error` with reasons and grant references. `keel.PermissionGate` and `GuardedInvoker` layer Keel checks behind that decision without widening it.
- [x] **addressed in the Charter adapter** — `keel.Gate` runs at every boundary without importing keel's `handler` or `worker` packages (they pull the cloud SDKs): `Middleware(routes)` for HTTP including generated CRUD paths, `Handler(capability, inner)` for table actions and custom endpoints in the same place `handler.WrapTableAction` sits, and `Check` with `JobContext` for workers, which bind the principal claimed with the job. The gate establishes the active identity and an effective grant and passes a `Clearance` down the context; the invoker keeps limits, approvals, separation of duties, and information governance. The pre-action port above stays a proposal for keel, to be raised only if a downstream needs in-band gating that the route table cannot express.

## Invocation and evidence

- [x] **addressed in the Charter SDK and adapter** — `capability.Invoker`, `Invocation`, and `Result` carry actor/runtime context, contract version, resource context, idempotency, structured domain outcomes, denials, failures, and evidence references. `keel.GuardedInvoker` adds request correlation and Keel trust guards.
- [x] **addressed in the Charter SDK and adapter** — `evidence.Sink` accepts action, evidence, exception, escalation, and integrity-bearing bundle records. `keel.TableLogStore` appends them with partner/owner scope snapshots, and `PublishingSink` emits the appended document.
- [x] **addressed in the Charter adapter** — `TableLogStore` snapshots and applies partner/owner scope (keel v1.2.55), `evidence.BaseRedactor` masks credentials before storage, and `TestTableLogStorePreservesNamespacesAndExtensions` proves a document with namespaced `extensions`, a cross-namespace `enterpriseId`, and free-text sources reads back from the store and reaches the publisher semantically unchanged, keyed by its own namespace. `TableLogStore` needs a queryable `port.TableLogger`; keel's filesystem logger is write-only, so a queryable destination (SQL over `port.QueryService`, cloud logging) is the next `port.TableLogger` implementation to write. It carries no Charter terms, so it belongs upstream in keel once one project has proven the shape.

## Validation and conformance

- [x] **addressed in the Charter SDK** — `validate.Validator` and `validate.Rule` return `Finding` values containing rule id, requirement ids, verification class, namespace/document, path, and message for structural and semantic validation.
- [x] **addressed in the Charter SDK and CLI** — `validate.Runner.Claim` and `charter claim` produce a schema-valid `ConformanceClaim` carrying specification and profile, implementation version, tested rules, result date, per-rule outcomes with verification class, and `partial` when a rule is untested; binding feature partiality is `binding.Conformance`. The claim is a document the caller persists, so no sink port is needed in keel or Charter.
- [x] **addressed in the Charter adapter** — `keel_test.go` proves requirement ids and statuses cross `GuardedInvoker`, `MetricsInvoker`, and `PermissionGate` unchanged and that namespaces, supersession, and bundle integrity survive `TableLogStore`; rule ids and verification classes cross no keel port. The remaining preservation fixture is the storage item above.
